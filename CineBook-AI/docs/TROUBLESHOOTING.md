# Troubleshooting

- **Java/Maven not found:** Install JDK 21 and Maven 3.9+, verify `java -version` and `mvn -version`, open a fresh PowerShell session, then rerun tests.
- **`Could not resolve placeholder 'app.jwt.secret'`:** Start the backend through Maven so `backend/src/main/resources/application.yml` is loaded: from the `CineBook-AI` project root run `./scripts/Start-Backend.ps1`, or from `backend` run `mvn spring-boot:run`. For a direct IDE launch, run a clean Maven build (`mvn clean package`) and confirm `backend/target/classes/application.yml` exists. The JWT service has a development-only fallback now, but do not use that fallback for a public deployment; set a unique `JWT_SECRET` of at least 32 bytes.
- **Frontend does not load:** Open a terminal in `frontend` and run `npm run dev`. The Node server serves `index.html`, `styles.css`, and `app.js`, and proxies `/api` to `http://localhost:8080`; confirm Spring Boot is running on port 8080. The frontend has no runtime npm dependencies or framework build step.
- **CORS issue:** The standard local Node proxy and Docker nginx proxy keep browser requests same-origin. If you bypass the proxy and call a separately hosted API, allow the exact frontend origin in `SecurityConfig`.
- **Dependency resolution/DNS failures:** Maven Central must be reachable for initial backend builds. The frontend itself does not download framework dependencies.
- **MySQL connection refused:** Ensure MySQL is healthy, the database/user exist, and `DB_URL`, `DB_USERNAME`, `DB_PASSWORD` match. Compose names must be `mysql` inside Compose but `localhost` for a direct host process.
- **MySQL syntax error near `accessible BOOLEAN` in V1:** `ACCESSIBLE` is a reserved keyword in MySQL. The fixed migration uses `is_accessible`, and the `Seat` entity explicitly maps to that column. After switching to the fixed project files, recreate the disposable local `cinebook` database with `scripts/reset-local-cinebook-db.sql` (this deletes all data), then perform a clean Maven rebuild before restarting.
- **Flyway says `Detected failed migration to version 1 (initial schema)`:** This means MySQL has a failed Flyway V1 history record, commonly left by an interrupted/previous migration attempt. It is not caused by the Java version. First decide whether the local `cinebook` database contains data you need. If it does, stop and back it up; do not drop the schema or delete the Flyway history row blindly, because MySQL DDL can leave partially-created tables behind. For a disposable local development database only, open MySQL Workbench as a database administrator and execute `scripts/reset-local-cinebook-db.sql`. This **deletes every table and record** in the `cinebook` database. Restart the application afterwards so Flyway can create the schema from V1. If a fresh database fails again, capture the *new* migration error (the SQL exception immediately above the Flyway stack trace); that will identify the original SQL/database problem.
- **Flyway/Hibernate validation failure:** Keep JPA `ddl-auto=validate`; do not create/alter tables manually. Back up any data before `docker compose down -v`.
- **Login returns 401:** Confirm backend seeded accounts on a fresh schema and use the documented development password. If an account was already in a populated DB, seed logic does not reset the password.
- **No shows/seat grid:** Seeded shows start on future dates in Asia/Kolkata. Verify showtime inventory was created; booking requires a live show and AVAILABLE seat.
- **Redis/Rabbit unavailable:** Core simulator booking does not require them with direct defaults. Disable `APP_REDIS_ENABLED`/set `APP_CACHE_TYPE=none`, and disable `APP_MESSAGING_ENABLED` while testing core flow.
- **Razorpay option not shown:** Expected unless `PAYMENT_MODE=RAZORPAY` and both key ID/secret are configured. Webhooks require a valid webhook secret and reachable HTTPS callback.
- **Ambiguous gateway result:** Do not create a new order automatically. Compare payment/order state with Razorpay test dashboard and reconcile manually.

- **Java version checker rejects Java 26:** use `scripts\run-local.ps1`. Direct mode accepts Java 21 or newer; Java 21 is the tested target. Docker mode uses a pinned Java 21 image and avoids host JDK compatibility differences.
- **Backend stays unhealthy in Compose:** the backend health check uses `curl`, installed in the runtime image. Wait for MySQL, Redis, and RabbitMQ health checks to pass before the app is considered ready.
- **RabbitMQ login fails after upgrading an older local checkout:** Compose provisions a dedicated `cinebook` RabbitMQ account for fresh data volumes. If an old RabbitMQ volume has already been initialized with different credentials, update the existing account/password in RabbitMQ or recreate only the RabbitMQ volume after backing up anything important. Do not remove database volumes unless you intend to delete local bookings and seed data.
